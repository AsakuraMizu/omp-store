# Workspace store
This workspace keeps the agent's working material in a store at `{{path}}`. Working material is what you create to get the work done, as opposed to what the user asked for: notes, research and review findings, scripts, reproductions, cloned sources, build trees and environments, baselines, scratch files. The user does not read the store and nobody tidies it; whoever uses an entry is responsible for it being right.
- Put working material in the store, not in new directories elsewhere in the workspace. Deliverables are not working material: changes to the repositories and files the user asked for go where the work or the user puts them. The system temporary directory is fine for files a single command needs, never for anything you will look at again.
- Create an entry with `store_put` before writing, and write only inside the directory it returns, organized however suits the work. Nothing goes directly under `{{path}}`.
- Make one entry per piece of work, such as a reproduction, a research question or a baseline run, and keep everything it needs inside: sources, environment, scripts, notes, results. Things that become useless together belong in the same entry.
- Give something its own entry only when a second piece of work needs it, typically a build environment shared by several reproductions. Move it out at that point, update the paths in the entries that used it, and have each of them refer to the new entry by path. Write those paths with the write or edit tool: using an entry then also counts as using what it refers to, which keeps the shared entry from expiring. Search results show these links; check them before dropping an entry others use.
- Search the store before starting something that may have been done already, such as reproducing a bug, running a baseline, researching a topic or setting up an environment. When an entry serves the same purpose, reuse or update it instead of making a second one. `store_put` also lists similar entries after it creates one; when one of them is the same thing, drop the new entry and use the old. To find something you know existed, search with `include_trash`.
- What you find there is a lead from an earlier session, not ground truth. Check what you rely on against the current code and state; the session each entry records can be looked up with `archive` when you need the reasoning behind it. When you verify that an entry is wrong, drop it, or correct it if only part is stale.
- Keep scripts and configuration that use store content inside the store, and run them from there.
- A store path written into a file outside the store is a dependency the store cannot see, so the entry can expire under that file.
- Drop the throwaway entries you made once the task is done. Entries nobody uses expire on their own, and using a trashed entry brings it back, so there is nothing else to clean.
- The user sees only your replies. When something in the store matters to them, put the needed part in your reply; whenever you drop an entry, say which one and why.
